# Synthetic arrival phase v1

This bounded Core contract defines a native, isolated arrival-phase transition
for the repository-owned synthetic fixture; it is not wired to campaign creation
or Host. Inputs must resolve exactly to the built-in profile. The setup identity
binds that profile, the Land sequence ruleset and a synthetic declaration that
no non-land arrival obligations exist at turn 1/stage 1. It must not change the
meaning of any historical `ExplicitNone` policy or be reused as evidence for a
historical scenario.

The phase is bound to a caller-specified stable campaign ID and starts at the
exact turn-1/stage-1 Naval Convoy Arrival position from
`Cna1979LandSequence` with the profile's reconstructed initial world. Only the
Axis owner may select the profile's one group and destination. The command is
bound to the campaign ID, setup hash and expected state version. Invalid campaign,
setup, actor, slot,
group, destination, stale or repeated commands reject before mutation. Arrival
creates the unit and independent representation together, then advances to the
Land sequence's Fleet Assignment successor. There is no RNG draw.

A versioned event contains the setup identity, full command, resulting version,
arrived unit IDs and exact successor position. Its bounded canonical UTF-8 JSON
codec rejects unknown or duplicate fields and any noncanonical bytes by
re-encoding; decoding alone does not validate effects or authorize an event.
Replay must start from the trusted profile and expected campaign ID and
recompute the entire event and world; altered bytes, version, actor,
unit list, setup or successor reject. An accepted retry must return the retained
original event, and conflicting reuse must fail. Event encoding here is internal
until integrated with the existing campaign serializers and authenticated journal.
A valid event or hash alone is not authority; callers must authenticate history.

The bounded opening returns the eligible group and destination only to its Axis
owner while the phase is pending. Other sides receive an empty offer list both
before and after the arrival; that empty result contains no state version,
schedule, event or successor position. This is not seat authentication or the
Host's opaque-reference protocol.

The version-1 synthetic checkpoint stores the campaign ID, setup hash, phase state version,
position ID and either no event or one canonical event. A reader reconstructs
the world and receipt solely by replaying that event from the fixed profile,
then compares the caller's expected campaign ID, every checkpoint field and re-encoded byte. A fabricated world,
position, version, event, or trailing field cannot be admitted by the checkpoint
reader. It is a phase checkpoint only, not a campaign save or a durable journal.

## Setup identity

A version-1 canonical setup envelope binds the fixed profile hash, start and
successor position IDs, and the synthetic-only `no-other-arrival-obligations`
policy. Its SHA-256 hashes the exact canonical bytes. Resolution requires exact
matching repository-generated bytes and expected hash; callers cannot authorize
a different schedule by supplying a new self-consistent hash. Existing setup
codecs and `ExplicitNone` remain unchanged. This setup object is not yet a
`CampaignCreationRequest`-admitted setup.
Its fixed hash is `sha256:0db4b957cad11cfe2d7189bbe01eab58de105c741332cfb402e7b3ba86a0b847`;
unexpected changes fail closed instead of silently changing this version.
